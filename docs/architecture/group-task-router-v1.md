# 群聊任务路由 V1

## 模式

群聊创建时写入 `collaborationMode`，默认是 `discussion`，也可以选择 `task`。模式属于群聊会话而不是某一条消息；标题区域可以通过窄 PATCH 接口切换并持久化。

```text
discussion                         task
全员参与多轮讨论                    先生成轻量任务分配
每个成员都有真实发言轮次             角色 + 技能/步骤状态
执行细节进入轨迹                    tool/reasoning/执行事实只进轨迹
```

任务模式不是把聊天变成工具日志。聊天只呈现用户消息、角色最终回复和一个轻量的任务协作卡；卡片只展示负责人、技能或步骤标题和 `待开始 / 进行中 / 已完成 / 已阻塞` 状态。完整的 Skill Action、工具调用、推理摘要和执行错误继续由 World Trace 投影。

## 持久化计划

SQLite schema v26 是群聊模式和任务计划的权威数据源。每个任务计划绑定一个世界、群聊会话和工作回合：

```text
WorkSession collaborationMode=task
└─ WorkTurn
   └─ TaskCollaborationPlan
      ├─ TaskCollaborationStep
      └─ TaskCollaborationStep
```

步骤保存所需技能、负责人、依赖、并行或顺序执行方式和当前状态。计划和步骤使用修订号进行并发更新；已完成、失败、取消或中断的状态不能重新回到运行中。服务重启会把运行中的计划及所有未完成步骤标记为中断，不会猜测或重复执行已经开始的任务。普通历史清理不会删除任务计划。

## 路由边界

- 创建群聊：`POST /api/worlds/:worldId/group-sessions`，请求包含 `title`、`employeeIds`、`collaborationMode`。
- 切换模式：`PATCH /api/sessions/:sessionId/collaboration-mode`，只改变当前群聊模式，不改变成员或历史消息。
- 任务计划：`GET /api/turns/:turnId/collaboration-plan` 是工作回合范围的正式接口；`GET /api/sessions/:sessionId/task-plan` 返回该群聊最近一次任务计划，供当前工作台轻量展示。
- 发送消息时，任务群聊使用 `interactionKind: task`，讨论群聊继续使用多人讨论语义。真正的执行路由、角色技能筛选和步骤推进由服务端/Runtime 负责。

任务路由是确定性的，不额外调用模型分类。它只读取显式提及、角色当前修订中的技能授权、当前世界可用技能、技能声明的路由词、角色职责和当前负载。默认选择一个最佳执行角色；任务包含多个匹配能力时最多选择三名。技能目录只参与选人与管理，不会被整体注入角色上下文。

例如“查官网并做 HTML 分析页”会把联网搜索和软件实现分配给匹配角色，不让无关的叙事角色重复执行。存在“然后、完成后、接着”等顺序关系时，后续步骤依赖前一步的真实回复；无依赖且由不同角色负责的步骤可以并行。所有执行都在同一个 WorkTurn 中创建独立 AgentRun，最后由明确的协调角色读取真实步骤结果并生成汇总。讨论模式继续保留所有成员按轮次发言的原有语义。

## 交互与可访问性

群聊对话框默认聚焦搜索框一次；后续 `creating` 或父级重渲染不会抢走用户正在填写的群聊名称。模式选择使用原生 radio，讨论默认选中，按钮和模式卡保持键盘可达。

## 验收

1. Web 组件测试覆盖讨论默认、任务切换、创建请求携带模式，以及搜索初次聚焦不抢群聊名称。
2. 持久化测试覆盖世界隔离、依赖环拒绝、状态转换、并发修订、重启中断和历史清理保留。
3. Chromium E2E 使用三名角色（联网搜索、软件实现、叙事技能）验证任务目标只分配前两名，协调汇总仍关联同一个 WorkTurn，讨论模式继续让三名角色参与轮次。
4. 三个视口检查群聊对话框和任务协作卡无横向溢出；记录 console error/warn 与 pageerror。聊天不出现 tool/reasoning 原始条目，轨迹仍可查看执行细节。
