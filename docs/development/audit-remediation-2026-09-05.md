## 执行方式

先验证发现仍成立，再以故障注入测试固定行为，最后实现修复。E1 独立语义复现必须转为仓库回归测试；E2 核对完整调用链；E3 保留为待验证风险，不能写成线上事故。

按以下顺序形成独立提交及审查单元。当前批次验证通过后继续下一批；公共契约变更由主 agent 统一整合，Luna max 子 agent 负责不冲突的实现、测试或审阅。每批记录测试结果、限制、提交号；未通过门禁不得标记完成。开发过程只使用隔离临时数据进行故障测试。

如拆分后续 PR，每个新开发分支重新 fetch 并从当时 `origin/main` 创建；依赖尚未合并时先处理依赖，不从旧开发分支宣称最新基线。本轮一个整改分支内按顺序提交，不重复创建相互依赖的平行实现。

## 验证与交付标准

1. 每批运行受影响测试、类型检查与构建；跨契约修改追加相关服务集成测试。
2. 界面修改使用真实可见控件，记录 1440×900、1920×1080、3840×2160 的图片适配、空白、对比度、中文一致性、最小字号、可读性以及 console error/warn。
3. 真实 Harness canary 与无密钥确定性测试分别报告；没有真实执行证据不宣称供应商链路已通过。
4. 提交前检查差异范围及运行健康；不提交凭据、数据库、日志、生成产物。提交后 push，按精确提交检查 CI；合并与发布只采用实际通过的证据。
5. 备份/恢复测试不操作用户 stateRoot；更新不能删除本地世界、角色、资产或历史。
