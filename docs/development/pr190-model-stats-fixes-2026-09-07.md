# PR #190 模型统计维护者修复

## 来源与基线

保留 vlfiny 的 `d723728c7322f2a6170b1c8738203ead1aea6b04` 原始贡献与双栏布局，从当时的 `main@7d6fa682214aad98aa1a4c7e38e6438c6547e3da` 建立维护者分支，快进到该 PR 的集成提交。没有把未合并的 #191 一并引入。

## 发现与修复

- 原 SQL 选择 `tool_call_count`，JS 累加 `tool_calls`，导致工具数恒为零。改为 SQL 聚合真实列，避免将全量原始日志加载到 JS。
- 日志的 `provider` 原本是模型配置显示名，不能用服务商显示名过滤；重复名称、改名和删除都可能造成误归属。新增持久化的连接 ID / 名称快照，使用不依赖显示名的筛选键；所有聚合与名称查询限制于当前工作区。
- 服务商侧栏从当前时间窗口独立读取，不随选中的服务商收缩；旧日志仅作为明确标注的历史来源，不根据当前模型配置倒推历史连接。
- 原统计声明缓存字段，却没有保存真实 cache hits。v49 增量迁移新增可空字段；缺失与明确报告的零分开，缓存只计入输入的子集，不叠加为额外输入。
- 时间选择由枚举状态管理，一次变更触发一个带快照参数的请求。AbortController、清理标记及结果键拒绝旧请求回写；刷新不命中永久缓存，切换工作区不复用旧数值。
- 严格校验统计分组、服务商筛选、ISO 日期和起止顺序；非法输入返回明确的 422，不能呈现为零用量。
- 拆出独立统计面板，保留双栏、输入/输出用量、系统/角色分组与模型明细；补齐真正空结果、加载、错误状态、小屏表格滚动及本地化标签。

## 数据与运行边界

v49 只增加 nullable provider/cache 列与统计索引，迁移沿用现有迁移前备份和事务，不重写既有日志、不引入用户数据目录。对话与图片回合、模型发现入口在发起前捕获服务商快照，避免运行中修改配置导致归属漂移；后台知识记录在其现有交互回调使用精确 profile ID 记录。统计按已记录的交互/运行回合计数，不宣称等于 worker 内部所有上游 API 请求数；未报告的图片 Token 不估算。

## 回归证据

先对原 PR 建立四个失败断言：工具数、筛选后完整来源列表、缓存持久化、逆序时间范围。修复后保留这些断言，并覆盖同名连接、删除/改名、运行中改配、工作区隔离、5000 条记录、旧库迁移及重启。

新增前端回归覆盖首次点击范围/服务商、迟到响应/错误、强制刷新、工作区变更及加载/空/错误区分。已有迁移测试的“降级到历史 schema”构造同步移除新列；生产迁移保持严格，未以幂等跳过掩盖错误。

浏览器测试入口是设置 → AI 模型 → 打开模型中心 → 模型统计，使用真实服务端和 SQLite 中的确定性用量记录，验证一次点击切换、正确连接 ID、刷新新记录及 1440×900、1920×1080、3840×2160、390×844 布局。截图与控制台作为 CI artifact 保存，不将这些测试日志称为真实外部模型业务请求。测试结论以 PR 最终 HEAD 的 CI 为准。

本地使用同锁文件的离线依赖与固定 Node 22.19.0 执行类型检查、构建和 Vitest；本地不能直接访问 GitHub，因此由本分支限定、校验补丁 SHA-256 的一次性流程同步。临时传输文件和工作流必须从最终分支树删除。维护者分支正常 CI 通过后采用保留历史的合并，使原贡献者提交直接可追溯；不修改分支保护。
