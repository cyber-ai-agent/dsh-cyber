# ADR 0011：同一个世界的两种画法

- 状态：Accepted
- 日期：2026-08-28
- 扩展：ADR 0009 的 Avatar Runtime V2、ADR 0010 的形象创建 Provider

## 背景

世界此前被切成三个互斥的入口：地图（Pixi 2D 世界）、2D（单角色）、3D（单角色 VRM）。

```ts
type WorldViewMode = 'map' | '2d' | '3d'
```

这把两个不同的问题压成了一个。「看整个公司」和「看某一个人」成了互斥选项，于是想仔细看某个角色就必须离开世界；而 3D 指的是一种单角色视图，不是画公司的一种方式。代码层面的后果是 `WorldRuntimeDock` 在两者之间二选一渲染，进入角色视图会卸载 `WorldCanvas`、销毁它的 WebGL 上下文，再挂载一个毫无关系的视图——地图和数字人因此像两个产品。

同时 `RendererKind` 早已预留 `'three-3d'`，但注册表只注册了 `'pixi-2d'`，`WorldCanvas` 又从主题清单读取渲染器，用户无从选择。

## 决策一：渲染方式与镜头是两个问题

```ts
type WorldRendererMode = '2d' | '3d'
type WorldCameraMode = 'overview' | 'focus' | 'follow'
```

主题仍然声明它是为哪种渲染器创作的，但**画法属于视图而非世界**：同一个公司用两种方式看，不会变成两个地方。旧的三个存储值被迁移而不是丢弃，上次停在 3D 的用户仍然回到 3D。

`follow` 只在 3D 提供——2D 世界是俯视的，无法跟着角色穿过场景，提供一个不起作用的控件比不提供更糟。

## 决策二：走路属于世界，不属于渲染器

这是整个改造成立与否的关键，也是最容易被忽略的一条。

服务端**不是**角色移动期间的位置权威。`projectWorldRuntime` 发出带完整路径的 `entity.route` cue，然后把 `entity.position` **留在起点**，直到后续事件把角色安置到目标；`WorldRuntimeEntityState.route` 被写入却没有任何渲染器读取。插值一直由渲染器自己做。

只有一个渲染器时这没问题。两个渲染器共用一个世界时它会致命：拆掉一个、建起另一个，新渲染器只能读到快照里那个过期的起点，于是全体角色被瞬移回各自本次行走的出发点。

因此走路移到 `WorldLocomotion`——纯算术，由渲染器之上持有，比任何一个渲染器活得久。

## 决策三：3D 办公室从既有世界推导，不另行创作

主题用 2D 描述自己：楼面尺寸、角色站位 anchor、带像素边界的可交互设施、导航网格。这足以搭出一间办公室。

于是**没有任何东西是为 3D 单独创作的**。但要分清两种情况：可交互设施在两个渲染器里是同一个对象（同 id、同边界，所以点击含义相同）；桌子不是——2D 把家具画进背景图，3D 的桌子是从角色工位 anchor 推出来的，它站在该站的位置，但不是同一张桌子。分区沿用 `compileWorldSemantics` 已有的推断方式（按 anchor id 与 tag 关键词），引入第二套关于"会议区在哪"的意见，会表现为角色跑到楼面认为是工位的地方开会。

比例锚定在仿真自己的 86px 工位网格读作 1.6m 的桌距上，得到约 33m × 21m 的楼面——一个可信的楼层，而不是为了让 demo 好看挑的数字。

## 决策四：聚焦是移动镜头，不是更换画面

`WorldCanvas` 全程挂载。3D 下角色本来就在场景里，镜头移过去；角色面板标记为 `embedded`，保留姓名、状态、聊天与语音，但**不再自建头像舞台**——浏览器不会为同一个人给出第二个 WebGL 上下文，而这正是地图与数字人割裂的根源。

由此暴露并修正了三件事：

- 面板开合与镜头朝向是两个问题。绑在一起意味着退回全景的用户会连正在对话的聊天面板一起失去。
- 跑不动 3D 的设备被要求先下载 three 才能发现自己跑不动。降级阶梯的最后一级是 2D 世界，**这一级必须在不加载它要避免的东西的前提下到达**。
- 面板收到的是"用户上次偏好的渲染器"而不是"当前正在跑的渲染器"。

## 决策五：角色先在世界里，形象后到

选 3D 曾经会为没有形象的角色强行弹出编辑器。顺序反了：世界从角色存在的那一刻起就能画出所有人，把用户推去编辑器才能看见自己的公司，会让 3D 重新变成另一个产品。

没有形象的角色以默认低模出场，面板**常驻**提供创建入口。形象发布后世界就地采用它——不刷新、不离开办公室、不开第二块画布；模型真正就绪前替身一直在，所以慢下载表现为"这个角色还没变"，而不是房间里破了个洞。

## 决策六：动作机制接好，但不伪造素材

`VrmAnimationController` 一直能注册 clip 并交叉淡入，`MotionLibrary` 一直有资源 URL 字段，但两者从未连上——mixer 跑着一张空的动作表，所有动作都来自程序化骨骼操作。`loadMotionClips` 补上这条连接。

它**刻意不是动作的来源**。仓库不含任何动作素材，在这里硬造关键帧会得到比程序化更差的走路，却看起来像真实数据。没有声明 URL 时它什么都不加载，角色保留程序化层；主题或形象包一旦声明资源，立刻生效。

## 影响

- 现有 2D 世界行为不变，仍是正式模式而非降级。
- 首屏不含 three/three-vrm；构建预算是真实门禁，本次改动曾两次被它拦下（3D 目录名撞上 `/three/` 分包规则）。
- e2e 中 3D 渲染器不会运行：headless Chromium 只有软件光栅，而应用主动拒绝它。这一拒绝本身是被测行为；场景几何、构图与 LOD 由无需 GPU 的单元测试覆盖。

## 后记：一轮自审推翻的几条

这个 ADR 的第一版描述了几件代码当时并没有做到的事。一轮针对本分支的对抗性自审（四个维度、每条独立复核）确认了 36 条，去重后 22 个真问题，其中若干直接推翻上文的说法。记在这里，因为"注释说了代码没做"比没有注释更糟。

- **形象热替换当时不生效。** `resolveAvatarUrl` 被闭包在挂载那一刻，渲染器一直在问"世界刚打开时的角色名单"。决策五承诺的"不刷新、不离开办公室"是假的，直到它改为经 ref 读取。
- **东和西反了。** 绕 +y 正向旋转把 -z 转向 -x，所以东是负四分之一圈。四个方向错了两个，角色朝一边滑向另一边——正是 `rotateVRM0` 要防的那个毛病被重新引入。测试当时只验证两个函数互相一致，它们确实一致，只是一起错；现在断言模型前向量的实际指向。
- **换了形象的角色身体里会长出替身。** LOD 一变，`setDetail` 就把 `hideStandIn` 收起来的部件重新显示。
- **两个渲染器都读错了说话内容的字段。** projector 写的是 `excerpt`，2D 退化成显示活动标签，3D 干脆什么都不显示。这是既有缺陷，不是本次引入的。
- **决策六的"桌子是同一张桌子"说过头了。** 可交互设施确实是同一个对象（同 id、同边界，点击含义相同）；桌子不是——2D 把家具画进背景图，3D 的桌子是从角色工位 anchor 推出来的。它站在该站的位置，但不是同一张桌子。
- **`prefers-reduced-motion` 曾被当成"没有 GPU"**，直接不给用 3D。它的意思是"少动一点"。
- **LookAt 的文档描述了它没有的行为**：实际是脖子上的一条正弦，不看任何人。现在接受世界坐标目标，并按身体朝向换算。

以及一条判断修正：**§35 的会议编排其实是成立的**。`meeting.started` 会为每个参与者调用 `moveEntityToSlot(..., 'meeting', ...)` 发出真实路径 cue，两个渲染器都消费它——角色确实会走到会议桌。缺的只是"看向发言者"，那部分现在补上了。
